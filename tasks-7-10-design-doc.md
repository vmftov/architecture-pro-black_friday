## Задание 7. Схемы коллекций для шардирования данных

### Коллекция orders

**Типы данных**

```json
{
    "_id": objectId,
    "user_id": objectId,
    "created_at": date,
    "status": string,
    "total_price": decimal,
    "geo_zone": string,
    "product_items": [
        {
            "product_id": objectId,
            "price": decimal,
            "quantity": integer
        }
    ]
}
```

**Пример**

```json
{
    "_id": { "$oid": "AAAAAAAAAAAAAAAAAAAAAAAA" },
    "user_id": { "$oid": "BBBBBBBBBBBBBBBBBBBBBBBB" },
    "created_at": { "$date": "2026-08-19T07:25:00Z" },
    "status": "placed",
    "total_price": { "$numberDecimal": "47500.50" },
    "geo_zone": "Москва",
    "product_items": [
        {
            "product_id": { "$oid": "CCCCCCCCCCCCCCCCCCCCCCCC" },
            "price": { "$numberDecimal": "45000.00" },
            "quantity": 1
        },
        {
            "product_id": { "$oid": "DDDDDDDDDDDDDDDDDDDDDDDD" },
            "price": { "$numberDecimal": "1250.25" },
            "quantity": 2
        }
    ]
}
```

**Основной кандидат для шард-ключа:**

- user_id с хэшированием
    + Хэширование позволит равномерно распределить нагрузку по шардам.
    + При интенсивных запросах получения истории заказов пользователя и статуса заказа позволит ускорить поиск документа сведя его до поиска в одном шарде. Поиск заказа придётся производить не только по идентификатору заказа, но, сначала, по идентификатору пользователя. Идентификатор заказа можно проиндексировать.
    + Все заказы пользователя будут храниться в одном шарде, это позводит избежать поиска по нескольком шардам для отображения данных в профиле. 
    + Поиск по идентификатору заказа будет происходить во всех шардах, но это не типовая операция.

**Альтернативы:**

- geo_zone с хэшированием
    + Геозона имеет слишком мало возможных значений, а распределение пользователей по геозонам скорее всего будет неравномерным. Это приведет к появлению более горячих шардов в областях с крупными городами.
- (geo_zone по диапазону) + (user_id с хэшированием)
    + Позволит направить запросы от конкретных геозон к ограниченному числу шардов что хорошо распределит запросы при записи. 
    + Но, при запросах получения истории заказов пользователя и статуса заказа, поиск будет производиться во всех шардах.

**Команды MongoDB:**

```js
sh.shardCollection("mobile_world_db.orders", { "user_id": "hashed" });
```

### Коллекция products

**Типы данных:**

```json
{
    "_id": objectId,
    "name": string,
    "category": string,
    "price": decimal,
    "geo_zone_stock": [
        {
            "geo_zone": string,
            "quantity": integer
        }
    ],
    "properties" : object
}
```

**Пример:**

```json
{
    "_id": { "$oid": "CCCCCCCCCCCCCCCCCCCCCCCC" },
    "name": "Смартфон X",
    "category": "Электроника",
    "price": { "$numberDecimal": "45000.00" },
    "geo_zone_stock": [
        {
            "geo_zone": "Екатеринбург",
            "quantity": 50
        },
        {
            "geo_zone": "Калининград",
            "quantity": 30
        }
    ],
    "properties": {
        "color": "Цвет бедра испуганной нимфы",
        "os": "Astra Linux Mobile"
    }
}
```

**Основной кандидат для шард-ключа:**

- _id с хэшированием
    + Хэширование позволит равномерно распределить значения по шардам.
    + Поиск продукта (для списания остатков и отображения на странице продукта) всегда будет выполняться в одном шарде. 
    + Однако, поиск по категории или цене будет производиться на всех шардах. Т.к. данные о продукте меняются редко, эти горячие операции чтения можно слегка нивелировать добавлением secondary реплик на чтение и кэшированием.

**Альтернативы:**

- (category по диапазону) + (_id с хэшированием)
    + Позволит локализовать поиск в категории до нескольких шардов. 
    + Т.к. ни корзина, ни заказы, ни код бэкенда не знают категорию продукта, для всех этих операций (включая списания остатков, отображения на странице продукта, отображение данных в корзине и в карточке заказа) будут выполняться во всех шардах. 
- Шардирование по имени не принесёт пользы, так как операция поиска по имени не является горячей.

**Команды MongoDB:**

```js
sh.shardCollection("mobile_world_db.products", { "_id": "hashed" });
```

### Коллекция carts

**Типы данных:**

```json
{
    "_id": objectId,
    "user_id": objectId,
    "session_id": string,
    "user_or_session_id": string,
    "items": [
        {
            "product_id": objectId,
            "quantity": integer
        }
    ],
    "status": "active",
    "created_at": date,
    "updated_at": date,
    "expires_at": date
}
```

> Здесь **user_or_session_id** - специальное дополнительное поле для шардирования, в которое бэкенд, перед сохранением, записывает user_id, а если оно не задано, то session_id. Оно необходимо чтобы обойти ограничение MongoDB, запрещающее использование двух хэшированных полей в одном составном ключе. С помощью этого поля можно сделать шардирование независимым от того, залогинен пользователь или нет.

**Пример:**

```json
{
    "_id": { "$oid": "EEEEEEEEEEEEEEEEEEEEEEEE" },
    "user_id": null,
    "session_id": "Hfie73hfg9q0",
    "user_or_session_id": "Hfie73hfg9q0",
    "items": [
        {
            "product_id": { "$oid": "CCCCCCCCCCCCCCCCCCCCCCCC" },
            "quantity": 1
        },
        {
            "product_id": { "$oid": "DDDDDDDDDDDDDDDDDDDDDDDD" },
            "quantity": 2
        }
    ],
    "status": "active",
    "created_at": { "$date": "2026-08-15T20:05:00Z" },
    "updated_at": { "$date": "2026-08-15T20:15:00Z" },
    "expires_at": { "$date": "2026-09-15T20:15:00Z" }
}
```

**Основной кандидат для шард-ключа:**

- user_or_session_id с хэшированием
    + Хэширование позволит равномерно распределить нагрузку по шардам.
    + Все горячие операции завязаны на поиск корзины и в данном случае он будет производиться всегда в одном конкретном шарде.
    + При таком варианте все корзины одного пользователя будут располагаться на одном шарде. Маловероятно что один пользователь создаст так много корзин, что это приведен к существенному дисбалансу. 
    + Перемещение документов между шардами потребуется только после логирования анонимного пользователя, но эта операция не является частой и не должна привести к просадке по производительности.
    + Решение получается универсальным и покрывает горячие операции вне зависимости от того залогинен пользователь или нет.

**Команды MongoDB:**

```js
sh.shardCollection("mobile_world_db.carts", { "user_or_session_id": "hashed" });
```

## Задание 8. Выявление и устранение «горячих» шардов

Для мониторинга кластера можно использовать Prometheus и Grafana с расширениями MongoDB Exporter и Node Exporter. А также утилиты mongostat и mongotop.
При превышении определённых граничных значений Prometheus будет отправлять оповещения администратору кластера, выполнять скрипты.

### Метрики

1. Определение шардов (реплик), которые испытывают наибольшую нагрузку.
    * **Аппаратные метрики**
        + **CPU Usage** - стабильно высокие значения на репликах одного из шардов в противовес умеренному использованию CPU на других позволяет в первом приближении понять что он загружен больше остальных.
    * **Метрики реплики шарда**
        ```
        use mobile_world_db;
        db.serverStatus();
        ```
        + Тикеты операций **.queues.execution.write.available** и **.queues.execution.read.available** - если тикетов практически нет, значит реплика испытывает серьезные нагрузки. Позволяет понять тип нагрузки на запись и чтение.
        + Сетевые метрики **.network.bytesIn** и **.network.bytesOut** - позволяют увидеть объем записываемых и читаемых с реплики данных. Позволяет понять тип нагрузки на запись и чтение.
        + Очередь **.globalLock.currentQueue** - показывает число операция которые не успевают выполниться.
2. Определение причин загрузки шарда
    * **Метрики распределения данных по шардам и чанкам** (собираются с роутера)
        ```
        use mobile_world_db;
        db.products.getShardDistribution();
        ```
        + **.docs** - показывают распределение документов по шардам. Сильные отличия между шардами могут говорить о неправильно выбранном ключе шардирования.
        + **.chunks**, **.'estimated data per chunk'**, **.'estimated docs per chunk'** - показывают распределение чанков по шардам. Сильные отличия между шардами могут говорить о неправильно выбранном ключе шардирования. Если чанков мало при большом количестве документов или чанки большого размера, это может говорить о низкой кардинальности шард ключа.
         ```
        use mobile_world_db;
        sh.status();
        ```
        + **.chunks** - Наличие флага **jumbo** говорит о низкой кардинальности шард ключа и невозможности разделить чанк и распределить его по шардам.
3. Определение проблемных коллекций
    * **Данные утилиты mongotop**
        ```
        docker compose exec -it shard1-1 mongotop --uri="mongodb://shard1-1:27018"
        ```
        + Показывает сколько времени MongoDB тратит на чтение и запись данных в каждой коллекции. Позволяет увидеть самые нагруженные коллекции.
4. Определение проблемных значений
    * Высокая нагрузка может быть и при равномерно распределённых данных, если часть из них используется активнее. Чтобы определить что данные используются интенсивно, не смотря на хорошее распределение по шардам, можно считать кастомный коэффициент как отношение процента выполненных операций к проценты содержащихся в шарде данных. Первый процент можно рассчитать на основе данных serverStatus().opcounters, второй - предрассчитан в из db.products.getShardDistribution().

### Механизмы автоматического снижения высокой нагрузки

* Убедиться что балансировщик включен и работает
    ```
    sh.getBalancerState();
    sh.startBalancer();
    sh.enableBalancing("mobile_world_db.products")
    ```
* Разрешить чтение из secondary реплик или повыстить приоритет secondary реплик, чтобы разгрузить primary реплики
    ```
    db.getMongo().setReadPref('primaryPreferred');
    ```
    ```
    db.getMongo().setReadPref('secondaryPreferred');
    ```
* Настроить горизонтальное масштабирование:
    + добавлять новые реплики на чтение по мере роста нагрузки
    + добавлять кэш-узлы по мере роста нагрузки
* Предварительно произвести вертикальное масштабирование для узлов на которые будет ожидаемо высокая нагрузка, если позволяют ресурсы 
* Настроить запуск скриптов по событиям из Prometheus:
    + переносить холодные чанки из горячих шардов в другие шарды для освобождения ресурсов
    + принудительно разбивать горячие чанки
    + временно отключать балансировщик и мониторить изменение нагрузки

### Действия после падения нагрузки (окончания «черной пятницы»)

* Разделить один документ на несколько. Например, хранить региональные остатки отдельно и шардировать их по геозоне.
* Изменить ключ шардирования и выполнить решардинг на основе фактической статистики.
* Выполнить шардирование по зонам и соотнести популярные категории с более мощными шардами.
* Выполнить частичную миграцию данных в облако (Atlas cluster) и настроить автоматическое масштабирование кластера в периоды предсказуемой высокой нагрузки, такие как «чёрная пятница».

## Задание 9. Настройка чтения с реплик и консистентность

**Соответствие реплик и операций:**

| Операция чтения                                                | Реплика                                               | Обоснование                                             |
|:---------------------------------------------------------------|:------------------------------------------------------|:--------------------------------------------------------|
| **Коллекция orders**                                           |                                                       |  |
| Поиск истории заказов конкретного пользователя                 | primary или secondary c сессиями (Causal consistency) | Первые несколько минут - с primary, чтобы клиент увидел точный первичный статус "подтверждено"/"отклонено" для только что оформленного заказа, затем можно с secondary. Т.к. MongoDB не поддерживает maxStalenessSeconds < 90 сек, лучше использовать сессии с Causal consistency.  |
| Отображение статуса заказа                                     | primary или secondary c сессиями (Causal consistency) | Первые несколько минут - с primary, чтобы клиент увидел точный первичный статус "подтверждено"/"отклонено", затем можно с secondary. Т.к. MongoDB не поддерживает maxStalenessSeconds < 90 сек, лучше использовать сессии с Causal consistency. |
| **Коллекция products**                                         |                                                       |  |
| Чтение остатков для вычитания при оформлении заказа            | primary                                               | Требуется высокая согласованность, чтобы гарантировать, что один и тот же товар не назначен нескольким пользователям. |
| Чтение остатков для отображения в карточке продукта            | secondaryPreferred с задержкой 10 - 30 сек            | Достаточно конечной согласованности, т.к. имеет место естественный race condition. Даже читая с PRIMARY может получиться рассогласование, если второй пользователь оформит заказ, пока первый - читает. Чтобы сгладить ситуацию, когда пользователь обновляет страницу и вновь видит наличие товара, можно обтекаемо писать "товар заканчивается" если остатков мало. Когда продавец увеличит остатки, они обновятся достаточно быстро. В период распродаж нужно увеличивать ресурсы для уменьшения задержки обновления secondary узлов. В обычные дни можно держать более высококое время обновления. |
| Описание товара на странице продукта                           | secondaryPreferred с задержкой 600 сек                | Обычно продавцы готовятся к черной пятнице заранее, в пиковый момент активных изменений в описании продукта будет немного. _В худшем случае, ошибка в описании товара обновится достаточно быстро - у продавца уйдет гораздо больше времени на разобирательство действительно ли есть ошибка._ |
| Поиск товаров по категориям и фильтрация по диапазону цен      | secondaryPreferred с задержкой 300 сек                | Обычно продавцы готовятся к черной пятнице заранее, в пиковый момент активных изменений по характеристикам и ценам продукта будет немного. В заивисомти от того, является ли информация на сайте офертой, могут быть предприняты разные стратегии борьбы с несогласованностью. _В худшем случае, пользователю будет разрешено купить товар по неправильной цене или сообщено что цена изменилась в момент оформления заказа. Но это может привести к потере репутации магазина._ |
| Чтение цены продукта при оформлении заказа                     | primary                                               | Требуется высокая согласованность, т.к. придётся зафиксировать цену продукта в корзине в момент оформления заказа из-за оферты. Даже если есть ошибка. Потребуется сверка цен на товары с фактическими значениями в продукте. |
| **Коллекция carts**                                            |                                                       |  |
| Чтение данных корзины                                          | primary или secondary c сессиями (Causal consistency) | Требуется высокая согласованность, т.к. оформление заказа это договор с пользователем, а значит требуется точная информация о выбранных товарах из-за оферты. Читаем с реплики только если используются клиентские сессии, тогда можно полагаться на Causal consistency. _Если полагаться на eventual consistency для пользователя это может выглядеть как ошибка, если он сначала видел актуальную версию, а затем старую с реплики._ Если secondary недоступна, переключаться на primary. |

**Итоговые допустимые задержки обноваления реплик для коллекций:**

| Операция чтения                                                | replicationLag, сек | Обоснование                                             |
|:---------------------------------------------------------------|--------------------:|:--------------------------------------------------------|
| **Коллекция orders**                                           | 0                   | Из-за того, что активные и выполненные заказы хранятся в одной коллекции придётся применять стратегию которая подразумевает точную согласованность. |
| **Коллекция products**                                         | 10 - 30             | Из-за того, что остатки хранятся прямо в продуктах придется обновлять реплики чаще для того чтобы пользователи видели фактическое наличие товара. В обычные дни допустима более высокая задержка обновления, в распродажи нужно её снизить, что может потребовать масштабирования. |
| **Коллекция carts**                                            | 0                   | Корзина должна быть всегда актуальной. Отображение старой версии не допустимо. |

## Задание 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования

### Анализ операций

| Операция                                                         | Тип     | Данные, необходимые для выполнения операции |
|:-----------------------------------------------------------------|:--------|:--------------------------------------------|
| **orders**                                                       |         |                                             |
| Быстрое создание заказов с одновременным списанием остатков      | ЗАПИСЬ  | user_id, order_id                           |
| Поиск истории заказов конкретного пользователя                   | чтение  | user_id                                     |
| Отображение статуса заказа                                       | чтение  | user_id, order_id                           |
| **products**                                                     |         |                                             |
| Частые обновления остатков при покупках                          | ЗАПИСЬ  | product_id, geo_zone                        |

| Описание товара на странице продукта                             | чтение  | product_id                                  |
| **carts**                                                        |         |                                             |

### Сущности

|:-----------------------|:--------------------------|:-----------------------------|

## orders

**Описание:**

* Partition Key одинаковый для orders и order_items, чтобы все данные по заказам одного пользователя лежали на одном и том же узле, что положительно скажется на производительности запросов на чтение и запись.
* user_id имеет высокую кардинальность и позволит равномерно распределить данные пользователей по узлам, распределив нагрузку и на запись, и на чтение.
* Для выполнения операции "Быстрое создание заказов с одновременным списанием остатков" придётся организовывать распределённую транзакцию по паттерну Saga.

**Поведение под нагрузкой:**

* За счёт Leaderless-архитектуры Cassandra, добавление и обновление заказов разных пользователей может происходить одновременно и независимо на разных серверах.
* За счёт Consistent hashing, добавление новых узлов не приведёт к необходимости перемещения значительного числа данных и смещения нагрузки на новый узел.

**Согласованность:**

* Согласованность данных очень важна, т.к. заказ связан с юридическими и финансовыми обязательствами, поэтому при чтении заказов используется стратегия **Read Repair** и **Quorum** на чтение и запись.

## products

**Описание:**

* Для того, чтобы запросы на получение данных товара и поиска товаров выполнялись эффективно, выполнена денормализация.
* Таблица products содержит все данные товара и распределена по ключу product_id. Он имеет высокую кардинальность и позволит равномерно распределить товары по узлам, при выполнении операции чтения и обновления товаров.
* Таблица search_products_asc содержит описательные свойства товаров и служит для поиска. Чтобы поиск был эффективным, необходимо обеспечить высокую кардинальность категорий. Этого можно добиться двумя путями:
    1) Вручную разделить категорию "Электроника" и другие категории на подкатегории и распределить по ним товары. Необходимо обеспечить не менее 100 категорий, а лучше несколько сотен. 
    2) В Partition Key добавлено дополнительное поле category_bucket для искусственного увеличения кардинальности. Если разделить категории удастся, то его можно не использовать и оно всегда будет равно 1. Если не удастся, то следует выбрать для него диапазон значений, достаточный для равномерного распределения категорий по репликам. В процессе поиска будут опрашиваться все реплики содержащие определённую категорию. 
* Результаты поиска товаров возвращаются в порядке возрастания цен. Для получения результатов в порядке убывания цен, их можно реверсировать программно или добавить ещё одну денормализованную таблицу с обратной сортировкой.
* Остатки хранятся в таблице product_geo_zone_stock. Он позволяет эффективно и атомарно выполнять проверку наличия товара в заданной геозоне и уменьшать его.

**Поведение под нагрузкой:**

* Операции получения описания товара для отображения на странице продукта будут равномерно распределяться по репликам при запросе разных товаров.
* Если менеджеры магазина не создадут достаточное количество категорий, эффективность поиска может снизиться.
* LWT при проверке и уменьшении остатков потребует в 4 раза больше времени на выполнение. Если кластер не будет справляться, придётся хранить остатки в распределённом кэше, например в Redis. 

**Согласованность:**

* Таблица остатков требует высокого уровня согласованности, поэтому используется стратегия **Read Repair**. Для изменения остатков требуется **Quorum**. Для чтения достаточно **Local quorum**. Также, потребуется периодический запуск **Anti-Entropy Repair** для гарантии согласованности, особенно после сбоев.
* Для таблиц с товарами достаточно конечной согласованности. Её можно обеспечить с помощью **Hinted Handoff**. Также потребуется выполнять **Anti-Entropy Repair** для непопулярных товаров и восстановления после сбоев. Для чтения данных достаточно уровня согласованности **One**, т.к. данные по товарам обновляются редко, особенно в период распродаж. Для записи - **Quorum** или **Local quorum**.

**Создание таблицы и примеры запросов:**

```sql
CREATE TABLE products (
    product_id  UUID,
    name        TEXT,
    category    TEXT,
    price       DECIMAL,
    properties  TEXT,

    PRIMARY KEY (product_id)
);

CREATE TABLE search_products_asc (
    category        TEXT,
    category_bucket INT,
    price           DECIMAL,
    product_id      UUID,
    name            TEXT,

    PRIMARY KEY ((category, category_bucket), price, product_id)
) WITH CLUSTERING ORDER BY (price ASC, product_id ASC);

CREATE TABLE product_geo_zone_stock (
    product_id  UUID,
    geo_zone    TEXT,
    quantity    INT,

    PRIMARY KEY (product_id, geo_zone)
);

-- Атомарная проверка и уменьшение остатков
UPDATE product_geo_zone_stock SET quantity = quantity - 1 WHERE product_id = 33333333-3333-3333-3333-333333333333 AND geo_zone = 'Москва' IF quantity > 0;

-- Поиск товаров по категориям и фильтрация по диапазону цен
SELECT * FROM search_products_asc WHERE category = 'Электроника' AND category_bucket = 1 AND price >= 25000 AND price <= 30000;

-- Описание товара на странице продукта
SELECT * FROM products WHERE product_id = 33333333-3333-3333-3333-333333333333;
```

**Вывод:**

Коллекция products может быть мигрирована в Cassandra, однако потребуется дополнительная работа по увеличению числа категорий или внедрению бакетов категорий для увеличения кардинальности.

## carts

**Описание:**

* Сущности корзина нет, есть только сущности элементов корзины. 
    + Это позволит получать необходимые данные корзины за один запрос. 
    + Т.к. у пользователя не может быть нескольких активных корзин, в каждый момент времени, данный подход не приведёт к ошибкам. 
    + За это придётся платить дублированием значений полей status и дат. 
    + Потребуется дополнительная логика для изменения статуса и определении актуального значения дат. 
    + Т.к. количество операций чтения корзины обычно больше чем операций записи, данный подход позволит повысить производительность при чтении по сравнению с решением с двумя таблицами.
* В качестве Partition Key используется user_or_session_id, который содержит или id пользователя или id сессии с соответствующим префиксом для устранения пересечений.
* Partition Key гарантирует что все данные корзин одного пользователя будут лежать на одном и том же узле, что положительно скажется на производительности запросов на чтение и запись.
* user_or_session_id имеет высокую кардинальность и позволит равномерно распределить данные пользователей по узлам, распределив нагрузку и на запись, и на чтение.
* Удаление abandoned записей производится через TTL.

**Поведение под нагрузкой:**

* За счёт Leaderless-архитектуры Cassandra, добавление и изменение данных корзины разных пользователей может происходить одновременно и независимо на разных серверах.
* За счёт Consistent hashing, добавление новых узлов не приведёт к необходимости перемещения значительного числа данных и смещения нагрузки на новый узел.
* Партиции могут стать горячими, только если большое число активных пользователей, выполняющих неестественные действия (например, постоянное логирование и разлогирование или хаотичное добавление и удаление товаров в корзину) попадут в одну реплику. 

**Согласованность:**

* Согласованность данных очень важна. При получении неактуального состояния корзины, пользователь может начать совершать дублирующие действия по добавлению и удалению товаров или вообще отказаться от покупки. Поэтому при чтении данных корзины используется стратегия **Read Repair** и **Quorum** на чтение и запись (или **Local quorum** если требуется повысить скорость в пиковые моменты).

**Создание таблицы и примеры запросов:**

```sql
CREATE TABLE cart_items (
    user_or_session_id  TEXT,
    status              TEXT,
    cart_id             UUID,
    product_id          UUID,
    quantity            INT,
    created_at          TIMESTAMP,
    updated_at          TIMESTAMP,
    expires_at          TIMESTAMP,

    PRIMARY KEY (user_or_session_id, status, cart_id, product_id)
);

-- Получение текущей корзины для неавторизованного пользователя
SELECT * FROM carts WHERE user_or_session_id = 'session_id::Hfie73hfg9q0' AND status = 'active';
  
-- Получение текущей корзины для авторизованного пользователя
SELECT * FROM carts WHERE user_or_session_id = 'user_id::11111111-1111-1111-1111-111111111111' AND status = 'active';

-- Удаление товара из корзины
DELETE FROM cart_items WHERE user_or_session_id = '11111111-1111-1111-1111-111111111111' AND cart_id = 44444444-4444-4444-4444-444444444444 AND product_id = 55555555-5555-5555-5555-555555555555;
```

Коллекция carts может быть эффективно мигрирована в Cassandra.
