## Схемы коллекций для шардирования данных (задание 7)

### Коллекция orders

**Типы данных**

```json
{
    "_id": objectId,
    "user_id": objectId,
    "created_at": date,
    "status": string,
    "total_price": decimal,
    "geo_zone": string,
    "product_items": [
        {
            "product_id": objectId,
            "price": decimal,
            "quantity": integer
        }
    ]
}
```

**Пример**

```json
{
    "_id": { "$oid": "AAAAAAAAAAAAAAAAAAAAAAAA" },
    "user_id": { "$oid": "BBBBBBBBBBBBBBBBBBBBBBBB" },
    "created_at": { "$date": "2026-08-19T07:25:00Z" },
    "status": "placed",
    "total_price": { "$numberDecimal": "47500.50" },
    "geo_zone": "Москва",
    "product_items": [
        {
            "product_id": { "$oid": "CCCCCCCCCCCCCCCCCCCCCCCC" },
            "price": { "$numberDecimal": "45000.00" },
            "quantity": 1
        },
        {
            "product_id": { "$oid": "DDDDDDDDDDDDDDDDDDDDDDDD" },
            "price": { "$numberDecimal": "1250.25" },
            "quantity": 2
        }
    ]
}
```

**Шардирование**

Кандидаты для шард-ключей:

- user_id с хэшированием
- geo_zone с хэшированием

Объяснение:

- Шардирование по хэшу идентификатора пользователя (который сам по себе является частично случайным значением) позволит равномерно распределить нагрузку по шардам при интенсивных запросах получения истории заказов пользователя и статуса заказа и ускорить поиск документа сведя его до поиска в одном шарде. Все заказы пользователя будут храниться в одном шарде. Маловероятно, что один пользователь сделает так много заказов, что это приведет к серьезному дисбалансу в шардах. Однако поиск по идентификатору заказа будет происходить во всех шардах, но это не типовая операция.
- Шардирование по хэшу геозоны позволит направить запросы от конкретных геозон к конкретным шардам. Но оно может не дать результата, если основная нагрузка приходится от пользователей из одной-двух крупных геозон.

Альтернативы:

- Шардирование по дате заказа или цене привело бы к неравномерному распределению документов по шардам.
- Шардирование по списку товаров (в виде композитного значения) сложно и вероятно привело бы к неравномерному распределению документов по шардам.
- Шардирование по статусу не рационально, т.к. поле изменяется со временем и может принимать слишком мало различных значений для равномерного распределения. Кроме того, наиболее загруженным окажется шард с открытыми заказами, а остальные будут слабо задействованы.

Команды MongoDB:

```
sh.shardCollection("mobile_world_db.orders", { "user_id": "hashed" });
или
sh.shardCollection("mobile_world_db.orders", { "geo_zone": "hashed" });
```

### Коллекция products

**Типы данных:**

```json
{
    "_id": objectId,
    "name": string,
    "category": string,
    "price": decimal,
    "geo_zone_stock": [
        {
            "geo_zone": string,
            "quantity": integer
        }
    ],
    "properties" : object
}
```

**Пример:**

```json
{
    "_id": { "$oid": "CCCCCCCCCCCCCCCCCCCCCCCC" },
    "name": "Смартфон X",
    "category": "Электроника",
    "price": { "$numberDecimal": "45000.00" },
    "geo_zone_stock": [
        {
            "geo_zone": "Екатеринбург",
            "quantity": 50
        },
        {
            "geo_zone": "Калининград",
            "quantity": 30
        }
    ],
    "properties": {
        "color": "Цвет бедра испуганной нимфы",
        "os": "Astra Linux Mobile"
    }
}
```

**Шардирование**

Кандидаты для шард-ключей:

- _id с хэшированием
- (category по диапазону) + (_id с хэшированием)

Объяснение:

- Шардирование по хэшу _id позволит равномерно распределить продукты по шардам и ускорить их поиск. При выполнении операции получения описания товара на странице продукта, а также поиска продукта для изменения остатков будет задействоваться только один шард. Однако, при поиске по категории или цене потребуется задействовать все шарды.
- Шардирование по категории по диапазону позволит локализовать поиск в категории до нескольких шардов. Однако, т.к. количество категорий в общем случае небольшое, потребуется добавить дополнительное поле для избегания возникновения Jumbo chunk. Это значит что поиск только по идентификатору продукта потребует обращения ко всем шардам. Этот вариант покрывает второй тип операции, но не покрывает первый и третий.

Альтернативы:

- Шардирование по имени не принесёт пользы, так как операция поиска по имени не является горячей.
- Шардирование по цене или по остаткам (в форме композитного поля) привело бы к неравномерному распределению документов по шардам. Кроме того, поля изменяются со временем, особенно остатки, а значит потребуется частое перемещение документов между шардами.
- Шардирование по дополнительным свойствам описания товаров не рационально, т.к. разные товары имеют разные свойства и очень сложно предсказать распределение значений.

Команды MongoDB:

```
sh.shardCollection("mobile_world_db.products", { "_id": "hashed" });
или
sh.shardCollection("mobile_world_db.products", { "category": 1, "_id": "hashed" });
```

### Коллекция carts

**Типы данных:**

```json
{
    "_id": objectId,
    "user_id": objectId,
    "session_id": string,
    "user_or_session_id": string,
    "items": [
        {
            "product_id": objectId,
            "quantity": integer
        }
    ],
    "status": "active",
    "created_at": date,
    "updated_at": date,
    "expires_at": date
}
```

> Здесь **user_or_session_id** - специальное дополнительное поле для шардирования, в которое бэкенд, перед сохранением, записывает user_id, а если оно не задано, то session_id. Оно необходимо чтобы обойти ограничение MongoDB, запрещающее использование двух хэшированных полей в одном составном ключе. С помощью этого поля можно сделать шардирование независимым от того, залогинен пользователь или нет.

**Пример:**

```json
{
    "_id": { "$oid": "EEEEEEEEEEEEEEEEEEEEEEEE" },
    "user_id": null,
    "session_id": "Hfie73hfg9q0",
    "user_or_session_id": "Hfie73hfg9q0",
    "items": [
        {
            "product_id": { "$oid": "CCCCCCCCCCCCCCCCCCCCCCCC" },
            "quantity": 1
        },
        {
            "product_id": { "$oid": "DDDDDDDDDDDDDDDDDDDDDDDD" },
            "quantity": 2
        }
    ],
    "status": "active",
    "created_at": { "$date": "2026-08-15T20:05:00Z" },
    "updated_at": { "$date": "2026-08-15T20:15:00Z" },
    "expires_at": { "$date": "2026-09-15T20:15:00Z" }
}
```

Кандидаты для шард-ключей:

- user_or_session_id с хэшированием

Объяснение:

- Шардирование по хэшу user_or_session_id позволит равномерно распределить значения по шардам. При таком варианте все корзины одного пользователя будут располагаться на одном шарде. Маловероятно что один пользователь создаст так много корзин, что это приведен к существенному дисбалансу. Все горячие операции завязаны на поиск корзины и в данном случае он будет производиться всегда в одном конкретном шарде.
  Перемещение документов между шардами потребуется только после логирования анонимного пользователя, но эти операции не является частыми и не должны привести к просадке по производительности.
  Решение получается универсальным и покрывает горячие операции вне зависимости от того залогинен пользователь или нет.

Альтернативы:

- Шардирование по идентификатору корзины не принесёт пользы, так как операция поиска по идентификатору не является горячей.
- Шардирование по элементам (в форме композитного поля) привело бы к неравномерному распределению документов по шардам. Кроме того, поля изменяются со временем, а значит потребуется частое перемещение документов между шардами.
- Шардирование только по статусу не рационально, т.к. поле изменяется со временем и может принимать слишком мало различных значений для равномерного распределения. Наиболее загруженным окажется шард с активными корзинами. Такое шардирование не поможет в оптимизации типовых операций.
- Шардирование по любой из 3 дат приведет к неравномерному распределению значений.

Команды MongoDB:

```
sh.shardCollection("mobile_world_db.carts", { "user_or_session_id": "hashed" });
```
